# v1.3.0 class system

## Data and access

New class tables are additive. Existing user profiles, teacher connections, board JSON, assignments, completion events, exams, focus segments and their RLS policies are retained. `ders_classes` is an invoker wrapper over an explicitly authenticated private action entry point. Exposed tables have RLS and SELECT grants only; writes pass through live role, ownership, membership and archive checks. No service key is used in the client.

Active membership additionally requires the current approved teacher connection. Disconnecting it immediately revokes class access and excludes the student from active rankings. Leaving a class preserves the individual connection, personal records and historical class contributions. Rejoining never replays old rewards. Archived classes retain readable reports and stop new activities.

Invite links use 32 random bytes, are stored in a private table, and are replaced atomically under the class lock. Joining requires a student login and teacher approval. Approval also creates/reinstates the existing individual connection. Connected invitations need only student acceptance. One pending class request per student is enforced by a partial unique index. Request retries use unique operation IDs.

## Assignments and XP

The existing teacher composer, curriculum, draft storage and assignment RPC are reused. A class program creates a separate canonical assignment for each selected active member. Acceptance, repeats, custom week titles, change requests and report access keep their existing behavior.

Class XP has a separate append-only ledger. Canonical class assignment completions feed it through database triggers. Existing personal and competitive XP calculations are unchanged. A normal assigned task can produce a class reward only once; repeat events each have unique server identities. Personal tasks and individual teacher assignments cannot credit class XP.

Shared task rewards affect class XP only. A verified study segment is explicitly selected, must belong to the caller, match the subject and date window, start after membership began, and cannot be used in any other shared task. Stored net duration excludes paused time. Question contributions are explicitly labelled self reported. Positive integer quantities and idempotent operation IDs are validated on the server.

The database locks shared goals and settles the pool once when the valid total reaches the target before the deadline. Largest remainder allocation with a UUID tie break distributes exactly the integer pool in proportion to contribution. Zero contributors get no reward. Audited corrections use separate ledger adjustments. If a corrected settled task falls below target its pool is reversed and the task is cancelled permanently; later corrections cannot silently distribute the old pool again.

## Privacy and analysis

Sharing of name, exams and study duration defaults to false independently per class. Student responses remove peer IDs and private per-member progress. Opted-in summaries include only the chosen types. Teachers retain reports only through current approved individual connections. Peer exam averages/trend points require at least three result contributors; study aggregates require three active members. Historical membership and contribution records are retained for the teacher.

Exam summaries use each student's last non-partial result per exam and test-group scope within the chosen period; absent results are not zeros. TYT and AYT scopes stay separate. Trends are labelled daily last-exam averages. Study means include zero-study active members. Existing focus and exam data are read without rewriting them.

## Deployment and rollback

1. Run local PostgreSQL security/integration and browser checks; use synthetic staging Auth accounts only.
2. Inspect target schema before applying `20261030174259_class_system_v130.sql`. Use the protected transaction generated by `scripts/v130-migration.cjs`.
3. It makes a closed, server-only snapshot of prior public rows/accounts and the old RPC definition. It compares hashes of existing data and old RLS before commit; a mismatch rolls back the entire transaction. The snapshot never leaves Supabase. Retrying an installed migration is blocked.
4. Apply and verify staging first. Production migration requires release authorization for this new schema. Deploy the application only after the live schema passes the same guards.
5. Roll back application traffic to the recorded v1.2.2 deployment if needed. Keep additive class tables, events and new records; do not reset the database or restore an old whole-user snapshot over newer work. Any targeted recovery is separately reviewed.

The changes-request panel reuses `quest_change_requests`. The overview response adds teacher/program/subject metadata without rewriting requests. Student outgoing requests do not increment the teacher action badge; teacher incoming requests do. Existing notification keys prevent duplicate resolution notices.
